# Backend Interview Guide

이 문서는 프로젝트 설명 중 나올 수 있는 질문과 답변 논리를 정리합니다. 답변은 기술 이름보다 **문제 → 대안 → 선택 → trade-off** 순서로 설명하는 것을 기준으로 합니다.

## Q1. 왜 JavaScript Number 대신 Big.js를 사용했나요?

금융 계산은 반복적인 이자·수수료 연산이 발생하기 때문에 작은 부동소수점 오차도 누적될 수 있습니다. 정수 최소 단위로 환산하는 방법도 검토할 수 있지만 금리처럼 소수 값을 계속 다뤄야 했기 때문에 decimal arithmetic을 명시적으로 지원하는 Big.js를 사용했습니다. 단순 계산 속도보다 결과의 예측 가능성과 계산 의도를 우선했습니다.

## Q2. 왜 상환 방식 계산에 Strategy Pattern을 사용했나요?

원리금균등과 원금균등은 계산 정책이 다르고 이후 다른 상환 방식이 추가될 수 있습니다. 하나의 함수에서 조건 분기를 늘리는 방법보다 정책을 객체로 분리하면 시뮬레이션 흐름과 금융 계산 정책의 책임을 분리할 수 있습니다. 새로운 상환 방식 추가 시 기존 orchestration 코드를 최소한으로 수정할 수 있다는 점을 선택 이유로 봤습니다.

## Q3. 크롤링을 왜 Next.js 안에서 바로 하지 않았나요?

사용자 요청의 응답시간과 외부 사이트 크롤링의 처리시간·실패 특성이 다르기 때문입니다. 실시간 요청에서 크롤링하면 외부 사이트 지연이 그대로 사용자 latency에 전파됩니다. 그래서 데이터 수집과 정제를 Python 파이프라인으로 분리하고 PostgreSQL에 적재한 뒤 웹 서비스는 저장된 데이터를 조회하도록 구성했습니다.

## Q4. 왜 Kafka나 Redis Queue를 사용하지 않았나요?

현재 수집 규모에서는 별도 메시지 브로커가 해결하는 문제보다 운영 복잡도가 더 큽니다. 작업 수가 늘어 retry, scheduling, worker scale-out이 필요해지는 시점에 외부 Queue를 도입하는 것이 합리적입니다. 기술을 먼저 넣기보다 실제 병목과 장애 요구가 생긴 뒤 확장하는 Monolith-first 접근을 선택했습니다.

## Q5. DB에 UNIQUE와 CHECK 제약을 둔 이유는 무엇인가요?

애플리케이션 입력 검증만으로는 crawler, batch, SQL 등 다른 경로에서 잘못된 값이 들어오는 것을 완전히 막을 수 없습니다. DB 자체가 마지막 무결성 경계가 되도록 금리·기간 범위에 CHECK를 두고 상품 식별 조합에 UNIQUE를 두었습니다.

## Q6. 같은 상품을 두 번 크롤링하면 어떻게 되나요?

현재는 `(bank_name, product_name)` UNIQUE constraint가 중복 적재를 막는 1차 장치입니다. 향후 queue retry나 ingestion API를 도입한다면 source event id 또는 idempotency key를 저장해 동일 요청의 재실행 자체를 제어하는 방식으로 확장할 수 있습니다.

## Q7. 트랜잭션이 필요한 지점은 어디인가요?

단순 조회나 계산 자체보다 여러 DB 상태를 하나의 논리적 작업으로 함께 변경할 때 필요합니다. 예를 들어 상품 갱신과 수집 로그 기록을 반드시 함께 성공시켜야 한다면 하나의 local transaction으로 묶는 것을 검토할 수 있습니다. 외부 크롤링 네트워크 호출 전체를 DB transaction 안에 넣으면 connection과 lock을 오래 유지할 수 있으므로 외부 I/O와 DB transaction 범위는 분리하는 편이 안전합니다.

## Q8. 비관적 락과 낙관적 락 중 무엇을 사용할 건가요?

충돌 빈도와 실패 비용을 보고 선택합니다. 충돌이 드물면 version column을 사용한 optimistic locking이 대기 없이 처리량을 유지하기 좋습니다. 동일 row에 높은 빈도로 경쟁하고 반드시 순차 수정해야 한다면 pessimistic locking을 검토합니다. 단순히 동시성 문제가 있다는 이유만으로 distributed lock을 먼저 사용하지 않습니다.

## Q9. Redis 분산락은 언제 필요할까요?

애플리케이션 인스턴스가 여러 대이고 DB row lock으로 보호하기 어려운 외부 작업을 하나만 실행해야 할 때 후보가 됩니다. 예를 들어 여러 crawler worker가 동일한 수집 job을 중복 실행하지 않게 해야 하는 경우입니다. 다만 DB unique constraint나 idempotency로 해결할 수 있다면 그 방법을 먼저 사용합니다.

## Q10. 이 프로젝트에서 백엔드적으로 가장 중요하게 본 점은 무엇인가요?

단순 계산 화면보다 계산 정책 분리, 데이터 정밀도, DB 무결성, Web Runtime과 수집 Pipeline의 책임 분리를 중요하게 봤습니다. 향후에는 이 구조를 기반으로 idempotency, background job, transaction, 부하 테스트를 추가해 기능보다 신뢰성 측면을 더 확장할 계획입니다.

## 30-second summary

> 대환대출 서비스는 낮은 금리만 찾는 문제가 아니라 수수료와 상환 시점까지 포함해 총비용을 비교해야 한다고 보고 만든 의사결정 지원 서비스입니다. TypeScript와 Big.js로 금융 계산을 분리하고, 상환 방식은 Strategy Pattern으로 구성했습니다. Python 데이터 수집 파이프라인과 Next.js 웹 런타임을 분리하고 PostgreSQL의 제약조건으로 데이터 무결성을 보완했습니다. 현재는 불필요한 분산 시스템을 넣기보다 단일 구조에서 정확성을 우선했으며, 향후 실제 처리량 요구에 따라 Queue와 idempotency를 확장하는 방향으로 설계했습니다.
